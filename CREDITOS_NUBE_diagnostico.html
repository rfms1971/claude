Los otros tres «créditos», que no sirven acá

  • Créditos de API del Console (pay-as-you-go) — no se gastan mientras estés logueado con la suscripción.
  • Créditos de API mensuales del plan Max — textual: «can't be used in Claude Code or the Claude apps, including for extra usage».
  • Usage credits / extra usage — sí funcionan en Claude Code, pero son otra cosa: se habilitan en Settings → Usage, se facturan aparte a tarifa API, y entran después de que el bono se agote.

Lo que esto explica del protocolo

Qué se pierde si el check matutino no corre

El protocolo deja ver LEIDO que el chequeo tiene al menos dos puntos, y no se degradan igual:

PuntoQué lee¿Se recupera después?
Punto 2Filtra por ARCHIVO y lee el archivo entero (REGLA 4)Sí — se pierde latencia, no datos
Punto 1 / ACuenta filas de la DB (REGLA 3)No — es una foto del «ahora»

Como el punto 2 lee el archivo completo y no una ventana de tiempo, una corrida posterior sigue viendo lo que se escribió en los días salteados. En cambio un conteo de filas no se reconstruye: la foto de las 06:25 de un día que no corrió no existe y no se puede fabricar.

LEIDOY el punto recuperable ya tiene un falso negativo demostrado: la REGLA 5 registra que del 09-29 al 10-02 el log dio cero líneas con 129 corriendo. Cero no distingue «no pasó nada» de «pasa sin escribir línea».

El triaje, si hay que elegir

Solo la mitad-foto es sensible a la hora. Si no se puede correr el chequeo completo:

  • Capturar el conteo de filas a las ~06:25 cada día que no corra el chequeo. Es lo único irrecuperable.
  • El punto 2 puede esperar: una corrida el sábado cubre jueves y viernes sin pérdida.

INFERIDOPosible bloqueo, no verificado: si el chequeo necesita la DB y los archivos que viven en Chicago o Houston, una sesión de nube no los alcanza, y entonces correrlo a mano desde la nube no es opción. Eso hay que confirmarlo antes de planearlo.
